# Проверка бота автозакрытия выводов

Tampermonkey-скрипт: проверяет, правильно ли **«Бот_ПК закрытия тикетов выводов»** отвечает на тикеты по выводам, и находит тикеты, которые он должен был закрыть, но не закрыл. Скрипт **только читает** — история тикета и транзакция из отчёта Withdrawal requests. В тикетах ничего не меняется.

## Установка

Открыть ссылку в браузере с Tampermonkey и нажать **Установить**:

**https://raw.githubusercontent.com/partenkoEgor/proverka_bota_vyvodi/main/withdrawal_bot_checker.user.js**

> Пока изменения не влиты в `main`, ставить с ветки:
> https://raw.githubusercontent.com/partenkoEgor/proverka_bota_vyvodi/claude/confident-cori-8cded6/withdrawal_bot_checker.user.js

Работает на листах **Payment Support** (`paymentsupport`) и **List of payment queries (Extended)** (`ExtendedPaymentRequestList`) на доменах `th-managment.com`, `my-managment.com`, `managment.io`, `webmanegment.com`. Кнопка **Проверка бота** — слева внизу (над Double Mistakes и In Progress), или **Alt+B**.

## Как запускать

Тикеты задаются одним из двух способов:
- **фильтр** — выставить фильтр (период; удобно сразу выбрать темы «I didn't receive my withdrawal» и «Error while withdrawing funds») и нажать **APPLY**: скрипт перехватит запрос и пройдёт все страницы выдачи. Понимает оба вида списка: Payment Support (`page`/`perPage`, конец по `hasMore`) и расширенный (`numberPage`/`countOfItemPage`, конец по `total`);
- **список** — вставить Ticket ID в поле (разделитель любой).

### Рекомендуемый порядок — в два шага

Отчёт Withdrawal requests находит не все выводы, поэтому транзакции лучше брать из выгрузки базы.

1. **Шаг 1 — собрать номера транзакций.** **① По APPLY** или **① По списку**. Скрипт грузит только истории тикетов (без отчёта) и собирает Transaction ID нужных тикетов — тех, где отвечал бот, или подходящих по теме и типу. Номера идут одним столбцом, **частями по 5000** (лимит выгрузки из базы):
   - кнопки **📋 Часть N** копируют часть в буфер обмена;
   - автоматически скачивается `tranzakcii_dlya_bazy_<дата>.xlsx`: листы «Часть 1», «Часть 2»… (один столбец без шапки), «Тикеты» (Ticket ID → Transaction ID), «Не загрузилось».

   Собранный список сохраняется в браузере — переживёт перезагрузку страницы, пока делаете выгрузку.
2. **Выгрузить эти номера из базы** (по файлу на каждую часть).
3. **Шаг 2 — 📄 Загрузить выгрузку (можно несколько).** Можно выбрать сразу несколько файлов или добавлять по одному — они складываются. Панель покажет, сколько собранных номеров нашлось и **каких не хватает** (кнопки 📋 копируют недостающие — их можно довыгрузить и тоже загрузить). То, чего нет в выгрузках, скрипт поищет в Withdrawal requests.
4. **② Проверить собранные.** Проверка идёт по уже загруженным историям (без перезагрузки страницы — без повторных запросов). Тикеты, чья история не загрузилась на шаге 1, пробуются ещё раз.

### Сразу, без шага 1

**▶ По APPLY** / **▶ По списку** — проверка за один проход: история + транзакция (из загруженных выгрузок, если есть, иначе из Withdrawal requests).

- **Потоков (1–5)** — сколько тикетов грузится параллельно. При 429/5xx скрипт сам повторяет запрос с паузой (до 5 раз).
- **⏹ Стоп** — останавливает; на шаге 1 сохраняет то, что успел собрать, при проверке — выгружает проверенное.

### Транзакции из выгрузки базы (рекомендуется)

Отчёт Withdrawal requests показывает не все транзакции: многие выводы (Onlypay, Bank Ekspres, Smartpropay и т. п.) в нём не находятся — и у скрипта, и вручную. Поэтому транзакции лучше брать из выгрузки базы (xlsx или csv, до 5000 строк в файле — файлов можно несколько). Скрипт сначала ищет транзакцию в выгрузках, и только если её там нет — в Withdrawal requests.

Колонки ищутся по названию, порядок не важен:

| Колонка | Зачем |
|---|---|
| **Номер заказа** (обязательна) | = Transaction ID в тикете |
| **Статус** | п.8: «Одобрено» / «Отказ» — финальные, остальные нет |
| **Сумма**, **Валюта** | п.5, п.9 |
| **Сумма платежа**, **Валюта платежа** | пояснение, если тикет совпадает только с ними |
| **Дата совершения платежа** | п.6/8а, п.8б: когда транзакция стала финальной |
| Дата создания, Комментарий | для справки |

Проще всего выгружать ровно те номера, которые собрал шаг 1. Время в выгрузке совпадает со временем сайта: бот отвечает через 0–3 минуты после «Даты совершения платежа».

По каждому тикету делается запрос истории (`/admin/backoffice/paymentsupporthistory`) и, если тикет по теме и типу подходит, — запрос транзакции в Withdrawal requests (`/en/admin/report/requestwithdrawal` по ID). Одна транзакция запрашивается один раз за прогон.

## Что проверяется

Сначала скрипт ищет в истории запись бота: `Admin username = Бот_ПК закрытия тикетов выводов` с внутренним статусом **Response to customer** (или Customer status **Reviewed**). Тип, тема, статус, сумма и валюта берутся **из записи прямо перед ответом бота** — тип тикета за жизнь тикета может меняться (например, API → BT M).

| Пункт | Как проверяется | Откуда |
|---|---|---|
| 1. Тема 2 / 4 | `idTopic` | история |
| 2. Тип 1, 2, 5, 8 (A) / 4, 6 (M) | `requestTypeId` | история |
| 3. Статус для пользователя | Customer status перед ботом: New, In progress, Clarification data, Payment on its way, Approval of compensation, Contact customer support | история (`nameUserStatus`) |
| 4. Тикет не старше 30 дней | от первой записи истории до ответа бота | история |
| 5. Валюта | `currencyKode` тикета = `currency` транзакции | история + отчёт |
| 6 / 8а. Тикет создан раньше проведения транзакции | создание тикета < `date_payment` транзакции. Отдельной истории статусов транзакции нет, поэтому п.8а («на момент создания тикета статус не был финальным») проверяется этой же датой | история + отчёт |
| 7. Раньше не было «Ответа игроку» | до бота нет Response to customer / Reviewed | история |
| 8б. На момент ответа транзакция финальная | статус 2 (Одобрено) или 3 (Отказ), и `date_payment` не позже ответа бота | отчёт |
| 9. Суммы совпадают | `amount` тикета = `summa` транзакции. Для A расхождение допустимо (п.10), для M — бот не должен был закрывать | история + отчёт |
| 10. Сумма после ответа | для A после ответа бота сумма тикета = сумме транзакции; для M бот сумму не меняет | история + отчёт |
| 11. Ответ | Response to customer + номер шаблона в начале ответа: A — 579 или 28 (одобрено, оба считаются правильными), 5 (одобрено, сумма изменена), 4 (отказ); M — 411 (одобрено), 412 (отказ) | история (`answer`) |

## Excel `proverka_bota_vyvodi_<дата>_<время>.xlsx`

| Лист | Что там |
|---|---|
| **Ошибки бота** | бот ответил, но хотя бы один пункт нарушен (❌ в колонке пункта, причина в последней колонке) |
| **Пропуски** | бот не ответил, хотя на момент ответа человека (или сейчас, если ответа нет) все условия выполнены. В пояснении — кто ответил и через сколько минут после того, как транзакция стала финальной |
| **Ручная проверка** | данных не хватает, чтобы решить: отчёт не ответил, тикет создан в ту же минуту, когда проведена транзакция, транзакция стала финальной меньше 30 минут назад и т. п. (❓) |
| **Бот ОК** | бот ответил, все пункты соблюдены |
| **Не загрузилось** | история тикета не загрузилась после повторов |
| **Сводка** | итоги по листам и какие пункты бот нарушает чаще всего |

В каждой строке есть **Источник транзакции** (база / отчёт) и **Текст ответа**, который ушёл игроку.

Тикеты, которые под правила не подходят и которые бот правильно не трогал, в файл не выгружаются — только счётчик «Не под правила».

## Допущения

- **Время.** Даты истории — время сайта (+03:00). Даты отчёта приходят как `/Date(мс+0300)/` и переводятся в то же время; `dtPayTransaction` в истории совпадает с `date` транзакции, это подтверждает.
- **Дата проведения** транзакции — `date_payment` отчёта, с точностью до минуты. Поэтому одна и та же минута у создания тикета и проведения транзакции — «ручная проверка», а не ошибка.
- **Пропуски.** Если первым ответил человек, это не обязательно ошибка бота — он мог не успеть. Сортируйте лист «Пропуски» по пояснению: ответ через несколько минут после финального статуса — скорее гонка, через часы — бот действительно пропустил.
- **«Ответ игроку».** Считается ответом и внутренний статус Response to customer, и Customer status Reviewed — бот ставит оба.

Все списки (логин бота, темы, типы, статусы, шаблоны, 30 дней, 30 минут) — в блоке `RULES` в начале скрипта.
